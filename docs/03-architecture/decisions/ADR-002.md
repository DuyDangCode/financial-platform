# ADR-002: PostgreSQL with EF Core and InMemory Fallback

## Status

Accepted

## Context

The platform requires a relational database capable of enforcing strict data integrity, ACID transactions across multi-entity financial operations (`Order`, `Execution`, `Transaction`, `Position`), high-precision decimal arithmetic (`numeric(18,4)` and `numeric(18,8)`), and optimistic concurrency control.

At the same time, contributors and automated environments may want to clone the repository and run `dotnet run --project src/FinancialPlatform.Api` immediately to explore Swagger or test basic authentication endpoints without first starting Docker containers.

## Decision

1. **Primary Database Engine:** Use **PostgreSQL 16** (`postgres:16` in `docker-compose.yml`) accessed via **Entity Framework Core 8** and the `Npgsql.EntityFrameworkCore.PostgreSQL` provider as the authoritative source of truth for all financial and identity data.
2. **Optimistic Concurrency via `xmin`:** Use PostgreSQL's system column `xmin` as the concurrency token on mutable financial aggregates (`Portfolios`, `Positions`, `Orders`).
3. **Text-Stored Enums & Decimal Precision:** Map domain enums to `text` via `HasConversion<string>()` for human readability and safe schema evolution, and enforce explicit precision (`numeric(18,4)` for money/prices, `numeric(18,8)` for quantities) via `IEntityTypeConfiguration<T>`.
4. **Development InMemory Fallback:** In `Infrastructure/DependencyInjection.cs`, if `ConnectionStrings:DefaultConnection` is missing or whitespace, `AppDbContext` falls back to `UseInMemoryDatabase("FinancialPlatformDemoDb")`.

## Consequences

### Positive

- **Production-Grade Financial Integrity:** PostgreSQL provides robust transactional guarantees, composite unique constraints (used for execution/transaction idempotency guards), `xmin` optimistic locking, and `jsonb` storage for `AuditLogs`.
- **Zero-Friction Onboarding:** The API can boot in demo/fallback mode even if Docker is not running when the connection string is omitted.

### Negative / Trade-offs

- **Provider Divergence Trap:** The EF Core InMemory provider does **not** enforce relational foreign keys, unique indexes, `numeric` precision, transactions, or `xmin` concurrency tokens. Furthermore, running `dotnet ef migrations add` while configured for the InMemory provider produces invalid migrations. All migrations and integration tests must run against a real PostgreSQL 16 container.
