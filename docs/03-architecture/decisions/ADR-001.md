# ADR-001: Modular Monolith and Clean Architecture

## Status

Accepted

## Context

The Financial Portfolio & Trading Operations Platform models multi-step financial workflows encompassing user identity, portfolio management, asset market data, order lifecycle management, simulated order execution, immutable transactions, position accounting, and audit logging.

At the outset of the project, two primary architectural directions were considered:

1. **Microservices Architecture:** Separate deployable services for Identity, Portfolio, Trading, Market Data, and Audit communicating over HTTP/gRPC and a message broker.
2. **Modular Monolith with Clean Architecture:** A single deployable ASP.NET Core application partitioned into logical domain modules (`Identity`, `Portfolio`, `Trading`, `MarketData`, `Audit`) and strictly layered via Clean Architecture (`Api`, `Application`, `Domain`, `Infrastructure`).

Starting immediately with microservices for a single-developer / small-team learning and engineering platform introduces heavy operational overhead: distributed transactions across Order → Execution → Transaction → Position updates, network latency, schema synchronization, container orchestration complexity, and premature service boundaries before domain invariants are fully stabilized.

## Decision

We adopt a **Modular Monolith** structured around **Clean Architecture** and **Domain-Driven Design (DDD)** tactical patterns:

1. **Four-Layer Solution Structure:**
   - `FinancialPlatform.Domain`: Pure C# domain entities, value objects, enums, repository interfaces, and domain exceptions. Zero dependencies on frameworks, EF Core, or infrastructure libraries.
   - `FinancialPlatform.Application`: Use-case orchestration organized as vertical slices (`Features/<Module>/Commands|<Queries>/<UseCase>`), DTOs, and infrastructure abstractions (`Abstractions/`). Depends only on `Domain`.
   - `FinancialPlatform.Infrastructure`: EF Core `AppDbContext`, entity configurations, repositories, JWT/PBKDF2 identity services, and external adapters. Implements `Domain` and `Application` interfaces.
   - `FinancialPlatform.Api`: ASP.NET Core controllers, request/response models, `ApiResponse<T>` envelope, and `GlobalExceptionMiddleware`.
2. **No MediatR / In-Process Mediator Library:**
   - Command and query handlers are plain C# classes registered explicitly in `src/FinancialPlatform.Application/DependencyInjection.cs` and injected directly into controllers. This keeps call stacks transparent, avoids third-party pipeline magic, and makes dependency flow explicit.
3. **Logical Module Isolation:**
   - Each module (`Identity`, `Portfolio`, `Trading`, `MarketData`, `Audit`) owns its aggregates and tables. Cross-module workflows (such as order execution updating a portfolio position) are coordinated in the `Application` layer within a single database transaction rather than via ad-hoc cross-module table mutations.

## Consequences

### Positive

- **Strong Transactional Consistency:** Critical financial workflows (`Order → Execution → Transaction → Position`) execute within a single ACID PostgreSQL transaction without requiring distributed two-phase commits or sagas in the MVP.
- **High Testability:** `FinancialPlatform.Domain` and `FinancialPlatform.Application` can be unit-tested in milliseconds using lightweight in-memory fakes (`tests/FinancialPlatform.UnitTests`) without booting a database or HTTP host.
- **Low Operational Overhead:** A single `.NET 8` process plus a single PostgreSQL 16 instance (`docker-compose.yml`) is sufficient to develop, debug, and run the entire backend.
- **Clear Evolution Path:** Because modules communicate through explicit interfaces and maintain strict write ownership, individual modules can be extracted into standalone services in future phases if scaling or organizational requirements justify it.

### Negative / Trade-offs

- **Discipline Required:** Without physical process boundaries, developers must enforce module and layer boundaries through code reviews and project reference rules (e.g., never injecting `AppDbContext` into `Application` or `Api`, and never placing business logic in controllers or repositories).
- **Manual DI Registration:** Omitting MediatR requires registering every new command/query handler in `Application/DependencyInjection.cs`.
