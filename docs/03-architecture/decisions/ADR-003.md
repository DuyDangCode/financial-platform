# ADR-003: Stateless JWT Bearer Authentication with Stateful Refresh Token Rotation

## Status

Accepted

## Context

The Financial Platform exposes a REST API consumed by a Next.js web application (`frontend/financial-platform-web`) and potentially mobile or third-party API clients. The system must authenticate users securely (FR-001, FR-002), protect private portfolio and trading resources (FR-003, BR-036), and allow sessions to be revoked on logout or password change without requiring a database lookup on every read request.

## Decision

We adopt a hybrid **Stateless Access Token + Stateful Refresh Token** model:

1. **Access Tokens (JWT Bearer):**
   - Signed with `HMAC-SHA256` (`SymmetricSecurityKey`) using configuration under the `Jwt` section (`Issuer`, `Audience`, `Key`, `ExpiryMinutes` = 60).
   - Validated on every `[Authorize]` request with `ClockSkew = TimeSpan.Zero`.
   - Carries standard claims: `sub` (`User.Id`), `email` (`User.Email`), `name` (`User.UserName`), `jti` (unique token ID), and role claims (`role`) once RBAC persistence is wired.
2. **Refresh Tokens (Stateful & Rotated):**
   - Cryptographically random 64-byte opaque token (`RefreshTokenGenerator`), Base64-encoded, persisted in the `RefreshTokens` table with a 7-day lifetime.
   - Calling `POST /api/auth/refresh` validates that the token is active (`RevokedAt == null && DateTime.UtcNow < ExpiresAt`), revokes the consumed token immediately (`token.Revoke()`), and issues a fresh JWT + new refresh token pair (`AuthSessionIssuer`).
   - Calling `POST /api/auth/logout`, `change-password`, or `reset-password` revokes active refresh tokens so compromised sessions cannot be renewed.
3. **Password Hashing:**
   - Custom `PasswordHasher` implementing `IPasswordHasher` using `Rfc2898DeriveBytes.Pbkdf2` with `SHA-256`, `100,000` iterations, a 16-byte random salt, and a 32-byte subkey stored as `{base64Salt}:{base64Key}`, verified in constant time via `CryptographicOperations.FixedTimeEquals`.

## Consequences

### Positive

- **Fast Request Authorization:** Protected API endpoints validate JWT signatures and claims in-memory without querying PostgreSQL on every request.
- **Session Control & Revocation:** Refresh token rotation bounds the lifetime of stolen refresh tokens and ensures password changes/resets terminate long-lived sessions across devices.
- **Zero External Identity Dependency:** Works self-contained in local development and Docker without requiring Auth0, Keycloak, or ASP.NET Core Identity's heavy schema footprint.

### Negative / Trade-offs

- **Access Token Revocation Window:** An already-issued JWT remains valid until its `ExpiresAt` timestamp (up to 60 minutes) even after a user is disabled or logs out, unless a token denylist or shorter access token TTL (e.g., 10–15 minutes) is introduced in production hardening.
